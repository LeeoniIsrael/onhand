# Architecture — 6 October 2026

## Trust and data flow

The app submits intent; PostgreSQL decides whether an action is allowed. User-visible roles are immutable customer/worker roles created by the Auth signup trigger. Changing Auth metadata cannot promote a profile. Neither role can approve identity, credentials, insurance or payout readiness.

The client uses public Supabase credentials and authenticated RPCs. Raw tables use row-level security; writes are granted to validated transactions rather than arbitrary client inserts/updates. Private schema functions and service operations are inaccessible to anonymous and regular authenticated callers. Definer entry points have an empty search path and qualified references. The internal SQL ranker intentionally stays inlineable for worker-specific filters; it is revoked from clients and runs beneath those entry points.

`marketplace_action` is the command boundary. A caller supplies a UUID operation key and bounded JSON. The database locks the actor, validates ownership/role/status and records successful command results. Replaying identical input returns the result; reusing a key for different input fails. Keys are retained 30 days, so this is not an unlimited replay guarantee. The UI retains a failed command's key for a same-input retry. Read and command locks serialize one account, while separate accounts progress independently. Statement timeouts and hosted ingress limits should supplement transaction-level throttles; failures roll back DB throttle increments.

`marketplace_home` and `marketplace_job` return bounded projections, with keyset cursors for older jobs/messages. Worker coordinates and raw license documents are not public. Offers contain approximate region, kilometre distance buckets and five-minute ETA buckets; raw scores and metre distances are column-revoked, including Realtime. They contain no precise matching explanations. Exact addresses and photos require assigned-job access. Cancellation removes a worker's private-address/photo access. Short-lived photo URLs expire after five minutes and refresh in an open screen; already issued links remain valid until expiry.

## Runtime and interface

Three destinations: Home/Find work, Jobs and Account. Request creation has one description and price, an explicit category and address, optional timing/duration, and a review step. Job detail owns chat, progress, payment, photos, cancellation, reporting and reviews, avoiding parallel versions of the same flow. Legacy routes redirect to these screens.

Every authenticated RPC, raw-table policy and user Edge endpoint checks an active Auth session row as well as the profile; revoked/deleted sessions cannot keep using an unexpired JWT. Native sessions use UTF-8 byte-bounded Keychain/Keystore values with a generation manifest written last. Web uses tab-scoped sessionStorage plus a per-document Auth channel name to prevent cross-tab broadcasts mixing accounts. Sign-out clears the device immediately and requests server revocation; offline revocation may need expiry/recovery. Network calls have bounded deadlines. Old plaintext demo/Auth entries are removed. Private queries and request drafts remain in memory, and all cached account data clears on account changes/sign-out. A keyed screen tree prevents previous-account form state persisting in a new session. Tokens in web storage remain accessible to JavaScript, which makes HTTPS, CSP and trusted scripts important deployment requirements.

TanStack Query caches reads for 15 seconds, retains unused data for five minutes, deduplicates observers, and invalidates after writes. Home uses one 30-second polling observer, plus debounced Realtime signals owned once by the provider. Subscription instances use unique names because SDK channel cleanup is asynchronous; token refresh keeps the same actor subscription. Open jobs fall back to five-second polling if Realtime is unavailable and twenty seconds when connected. App lifecycle pauses background refresh; connectivity reconnects reads. Financial commands are never acknowledged optimistically or replayed blindly offline. Requests preserve their in-memory draft when navigating to addresses.

Controls have spring press feedback, native haptics, reduced-motion settings/system support, visible busy/error states and minimum touch targets. Job history is virtualized. Images resize to a 1,600-pixel longest side, are encoded as JPEG, limited to 8 MB and stored privately. An authenticated media endpoint validates content headers/dimensions and SHA-256 retry consistency, reserves actor/job quotas, and writes with server credentials. Direct Storage/signed uploads are denied; attachment requires an owned confirmed reservation and actual object. The cap is 100 upload reservations per actor/day, 24 per job and 12 attached photos. Foreground location updates support availability; there is no background worker tracking or paid routing integration. Travel estimates use straight-line distance and a rough speed multiplier.

## Matching and dispatch

Production matching is SQL over real eligible profiles, not the historical simulator. Hard filters run before scores: identity approval, good standing, payout readiness, availability, skill confidence, fresh location (15 minutes), service radius, minimum price, block lists, no active assignment, and current jurisdiction-specific credentials for regulated work. A PostGIS index prefilter limits the geographic search. Credential expiry must cover the later of now/appointment plus estimated duration. Regulated job coordinates must also fall inside an operator-approved jurisdiction polygon; claiming a jurisdiction label alone is insufficient.

Score components: Bayesian-smoothed review quality (34%), completion reliability (24%), skill confidence (18%), distance decay (14%), price fit (6%), and newcomer exposure (up to 4%). Twelve prior reviews at 4.5 reduce tiny-review-count distortions; reliability has a smoothed completion prior. Each other pending offer subtracts 4 percentage points; three pending offers is a hard cap. Job-specific hash ordering rotates ties deterministically. These weights are a transparent baseline, not a trained acceptance predictor or a promise of fairness/calibration.

Offers go out in bounded waves of 3, 6, 9, then 12 candidates, with five-minute urgent or ten-minute other expiration. Scheduled jobs enter dispatch within 24 hours. A worker gets one offer for a given job, including later waves. Dispatcher locks worker slots with SKIP LOCKED, rechecks eligibility, and reserves one of three uniquely indexed slots. Acceptance locks job then worker, rechecks qualifications, expires competing offers, and records one match. A partial unique index prevents two active assignments for a worker.

Event history and real completion/review metrics support future calibration. No paid AI, synthetic reputation, fabricated acceptance percentage, image diagnosis or automatic chat reply is used. A trained model needs real labelled outcomes, bias evaluation and an operator-approved budget; inserting an LLM does not improve this transaction boundary.

## Money and recovery

Stripe Express destination charges use USD card payments, manual authorization/capture and a 15% platform fee. Native uses PaymentSheet; web uses hosted Checkout. Authorization is limited to within 24 hours of a scheduled appointment. The worker cannot depart without an authorized payment and valid current qualifications. The customer must approve the current job version before capture.

Payment operation IDs persist before provider calls, supplying stable provider idempotency keys. Web/native authorizations cannot create separate holds for one job. Signed webhooks retrieve current provider state, and monotonic database transitions prevent late failure/authorization events undoing capture/refund. Duplicate captures create one ledger entry. Earnings are an internal transaction ledger; actual bank payout events are shown separately. Full refunds reverse earnings and destination transfers, with service-only support audit actions. Partial refunds, tipping and automated dispute decisions are not implemented.

A PostgreSQL outbox survives process failure. Capture/cancellation, notifications, receipts and media erasure are claimed in bounded batches; retry errors have backoff and a twelve-failure limit. Successful erasure chunks continue without consuming the failure budget. Operations reconcile provider state and clean old operational records. Notifications have generic lock-screen copy, device opt-in/preferences, batching, receipt checks, stale-token removal and account cleanup. Delivery is at least once; provider batch retries can produce duplicates. Notification taps accept only job UUIDs and use server-checked membership; offer taps open Find work.

## Scaling boundaries

There is no client-to-database connection per screen: HTTP RPCs and provider pooling manage connections. PostGIS, partial indexes, bounded queries, per-account/job locks and SKIP LOCKED protect common burst paths. This is a practical single-primary architecture for an early marketplace; availability depends on the chosen deployment, backups and operator response.

The local 5,000-worker benchmark is recorded in LOAD_TEST.json and the query plan in LOAD_QUERY_PLAN.json. It does not prove a concurrent-user SLA. Observe query p95/p99, lock waits, pool saturation, Realtime peaks and outbox lag on the actual hosted tier before expansion. Scale compute/pooling first; partition event history or split regional dispatch only when measured load warrants it. Keep financial writes on the authoritative primary. Do not add Redis as a second source of truth for assignment or payment state.
