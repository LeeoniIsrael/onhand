# Operations and launch runbook

No hosted project, payment account, paid plan or store account was created. These instructions are prepared for the operator; commands here have not deployed production. Never paste server keys into the app, a public issue or chat.

## Hosted setup, in order

1. Choose an existing Supabase project/region and budget. Make a backup of any existing database. Use a separate empty staging project first. Install/login to the official CLI, link the selected project (`npx supabase@latest link --project-ref YOUR_REF`), inspect `npx supabase@latest db push --dry-run`, then apply `db push` after reviewing the target. Do not use local reset/seed/test commands against a hosted database.
2. Configure Auth in the hosted dashboard: verified email signup, minimum password length 12, appropriate email/password rate limits, HTTPS site URL and allowlisted redirects. Install the confirmation/recovery HTML in `supabase/templates/`. Both must include `.Token` because the app verifies entered codes. Configure an SMTP sender you control; Supabase's default sender is unsuitable for general public signup. Test delivery, rate limiting, code expiry/reuse, recovery and sign-out. The local TOML does not automatically update hosted Auth settings.
3. Set public app environment values from `.env.example` in EAS development/preview/production environments. Use a publishable key or legacy anonymous JWT, never a service key. Use hosted HTTPS and `EXPO_PUBLIC_LOCAL_BACKEND=false`. Set the support email to a monitored contact. Link your EAS project and confirm bundle identifiers belong to you. Do not use the local fixture flag in a public build.
4. Prepare server secrets in a protected file and set them with `npx supabase@latest secrets set --env-file YOUR_PROTECTED_FILE`. Start with `PAYMENTS_MODE=disabled`, a random `OPERATIONS_SECRET` of at least 32 characters, and your HTTPS `APP_ORIGIN`. Later test payments with `PAYMENTS_MODE=test`, `sk_test_...`, `pk_test_...` on the client, and the test webhook secret. Hosted functions already receive Supabase server credentials. Never set `ONHAND_LOCAL_TESTS` on a hosted project. Optional Expo push access-token authentication is recommended before public push delivery.
5. Deploy the six handlers using `npx supabase@latest functions deploy payments`, then `stripe-webhook`, `account`, `connect`, `media` and `operations`. Their gateway JWT flag is false deliberately: each user endpoint calls Auth `getUser` and verifies the current server session; operations validates a server secret; webhook validates Stripe's signature. Do not replace those checks with a public API key. Verify anonymous, wrong-origin and wrong-role failures on staging.
6. Configure Stripe **test mode** Express Connect, card manual capture, connected accounts, and platform/Connect webhook destinations. Subscribe to payment intent status events, checkout completion/expiry, `charge.refunded`, `account.updated`, and `payout.*` for connected accounts. Register `/functions/v1/stripe-webhook` and install its signing secret. A platform endpoint and Connect endpoint may have separate signing secrets; deploy separate project/function environments or consolidate into one supported event destination with the matching secret. Do not feed unrelated signing secrets into this handler. Test 3DS, cancellation, interrupted authorization/capture, duplicate/out-of-order events, hold expiry, refunds, payout failures and reconnects. Native PaymentSheet and web Checkout must agree on the same job and amount. Live mode is a later operator decision with real processing costs.
7. Establish human identity, insurance and licensing review. Stripe bank/KYC onboarding does not establish trade qualifications. Use the audited operator tools below to approve evidence. Load accurate GeoJSON service polygons for each licensing jurisdiction before offering regulated work. No production polygons are seeded; the local test rectangle is deliberately synthetic. Verify address accuracy and define coverage/support/refund/retention policies. Do not store raw government IDs or full license documents in audit notes; store a protected evidence reference and decision rationale.
8. Enable operations only after deployed handlers/secrets pass staging tests. In a trusted SQL/admin session call `select public.configure_operations('https://YOUR_REF.supabase.co/functions/v1/operations','YOUR_STRONG_SECRET');`. It stores the endpoint/secret in Vault and creates the one-minute `onhand-operations` cron job. Never use the local sample secret. Confirm cron runs, HTTP results and `health_snapshot`. The scheduler is not active merely because migrations installed its function.
9. Link APNs/FCM credentials to the EAS project, make a development/release build and test opt-in, foreground/background delivery, taps, stale token cleanup and sign-out on physical devices. Then run the store gates in HANDOFF.md. No live push was sent during local verification.

## Operator commands

Set `ONHAND_OPERATOR_URL` and `ONHAND_OPERATOR_KEY` (server service key) in a protected shell environment, outside tracked files. Use a dedicated operator machine, restrict access, and rotate leaked credentials. These commands are intended for a trusted operator, not an app user:

```sh
npm run operator -- health
npm run operator -- workers
npm run operator -- reports
npm run operator -- review-worker WORKER_ID approve uninsured OPERATOR "Evidence reference and identity review decision"
npm run operator -- review-license WORKER_ID electrical.fixture NY 2027-01-01T00:00:00Z OPERATOR "Evidence reference and jurisdiction review"
npm run operator -- configure-region NY /protected/ny-service-geometry.json OPERATOR "Boundary source and operating coverage approved"
npm run operator -- open-dispute JOB_ID "Support case reference and reason"
npm run operator -- resolve-dispute JOB_ID completed "Provider capture verified and case resolved"
```

Use `insured` only after verifying insurance; `suspend` disables identity/availability and expires pending offers. Approving identity does not set payout readiness. Stripe events establish bank readiness. A changed worker name requires fresh identity review. Region files contain a GeoJSON **geometry** Polygon/MultiPolygon in WGS84, not a FeatureCollection. Review geography and licensing scope before loading; a valid polygon alone is not legal approval. To remove coverage, use a trusted administrative transaction to delete its private region row and record your decision; existing affected work needs support coordination.

Full refunds require an open support case and a captured payment. Call the protected operations endpoint with `{ "action": "refund", "jobId": "..." }` and the operations bearer secret. It uses a stable refund key, reverses transfers/application fees, and records a completed refund. Then resolve the case as `cancelled` only after provider confirmation. A pending/failed provider refund needs continued review. **Do not directly change payment states or mark a scheduled earnings ledger entry as a bank payout.** Partial refunds and automated disputes need further implementation before offering them.

## Daily checks and recovery

Monitor dispatcher queue, failed outbox rows, oldest pending-event age, cron HTTP failures, database query p95/p99, lock waits, connection pool saturation, Stripe reconciliation lag, signed webhook failures, Realtime connections and provider invoices. Review user safety reports promptly. The health RPC is service-only; never expose it with an operations secret in the mobile app.

Outbox processing is at least once. Keep handlers idempotent. A worker can claim up to 1,000 events; financial operations run in groups of ten. Notifications batch by 100 with pacing and check provider receipts later. One scheduler invocation is configured per minute; manually running extra concurrent invocations can exceed provider throughput, so do not treat per-process pacing as a global rate limiter. Errors back off; after twelve failures inspect `private.outbox.last_error`, repair the cause, and reschedule the failed row in a trusted session with attempts reset. Do not log tokens, photo URLs, chat text or private addresses to public monitoring.

The media handler streams at most 8 MB, validates JPEG/PNG/WebP headers and dimensions, and reserves uploads before service-side Storage writes. An actor has at most 100 reservations per UTC day and each job has at most 24 upload reservations, with 12 attached photos. Failed reserved attempts count toward those limits. Direct client and signed uploads are denied. Header parsing is not full image decoding or antivirus scanning. Configure hosted ingress/body/timeout limits and monitor failed attempts too; transaction throttles do not bound every invalid request or provider API call.

Media erasure removes 100 objects per successful chunk and reschedules remaining progress without exhausting failure retries. Account deletion blocks unresolved active jobs/financial operations, serializes against commands, removes Auth access and private addresses/settings/location, redacts authored messages/job details and queues photo cleanup. Minimal pseudonymous transaction/support records remain; define retention periods and handle deletion requests involving active disputes manually. Account erasure includes unattached uploads, including service-owned objects tracked by reservations. For active accounts, run a reviewed periodic inventory/cleanup of abandoned uploads (at least a 24-hour safety window); never delete registered objects by filename age alone. Actor mutation payloads and throttle rows are removed on deletion. Already issued signed links and backups have separate expiration/retention boundaries.

Choose a backup plan, test restoration into an isolated staging project, and verify migrations/RLS/financial totals after restore. Database backups do not by themselves back up all object storage. Keep independent encrypted storage backups if required. Rotate credentials and reconcile Stripe after a recovery. Set recovery-time/data-loss objectives; a successful local reset is not a hosted disaster-recovery drill.

## Capacity and deployment

Use the hosted HTTP/transaction pooler for any additional services; never create unbounded direct connections. Start with a measured workload on the chosen region/tier. A thousand registered accounts is different from a thousand simultaneous Realtime connections. Evaluate at least job-post bursts, acceptance races, chat bursts, large histories and provider slowdown before expansion. Increase compute/connection capacity based on measured p95/lock/pool lag. Realtime quotas and multiple tabs/devices affect cost.

For web hosting configure HTTPS, SPA fallback to index.html, HSTS, `X-Content-Type-Options: nosniff`, a strict origin-specific CSP and Referrer-Policy. Allow only your Supabase HTTPS/WSS endpoints and required Stripe endpoints; avoid broad wildcard scripts. The app's Edge CORS allowlist does not configure headers on a separate web host. Cache hashed static assets; keep Auth, RPC and payment responses private/no-store. No web host has been provisioned.

Deploy migrations/handlers first to staging, then compatible clients. Never roll back a financial schema by resetting production. Prefer additive migrations and forward repairs. Use `npm ci` so the tested lockfile and decoder import adapter apply. Recheck Expo versioned docs and the adapter before an SDK/Router upgrade. The remaining build-tool advisories are documented in the audit; do not force an Expo downgrade to make audit output appear clean.
